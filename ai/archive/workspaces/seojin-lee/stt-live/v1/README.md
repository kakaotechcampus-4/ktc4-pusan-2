# v1 — CPM 기반 말하기 속도 판정 (slow / normal / fast)

STT로 얻은 단어별 타임스탬프를 받아, 판정 구간의 **분당 발화 글자 수(CPM)**를 계산하고
**느림/보통/빠름** 세 단계로 판정하는 첫 번째 모델입니다. LLM 호출 없이 **규칙 기반(임계값
비교)**으로만 판정합니다.

```
STT 단어 타임스탬프          구간 슬라이싱        CPM 계산                임계값 비교
{word, start, end}[] ──▶ (예: 15초 윈도우) ──▶ (글자수 ÷ 발화시간) ──▶ (slow/normal/fast) ──▶ SpeedResult
```

이 문서는 **v1 모델의 전체 기술 레퍼런스**입니다 — 계산 방식, 출력 계약, 알려진 한계.
`local`과 `deploy`가 공유합니다.

> **코드를 돌려보려면 [local/README.md](local/README.md)** 로 가세요.
> 설치 절차, 노트북 실행 방법 같은 작업용 내용은 거기에 있습니다.

## 1. v1의 범위

**하는 것**

- STT가 이미 만들어낸 `{word, start, end}`(ms) 단어 리스트를 입력으로 받음
- 판정 구간(예: 15초) 안의 총 글자 수를 구하고, **실제 발화 시간**(단어별 `end - start`의 합,
  즉 침묵 제외)을 분모로 CPM(분당 발화 글자 수) 계산
- CPM을 두 임계값(`SLOW_THRESHOLD=275`, `FAST_THRESHOLD=350`)과 비교해 `slow`/`normal`/`fast`
  세 단계로 판정

**하지 않는 것**

- 음성 인식 자체(STT) — 입력은 이미 STT를 거친 단어 타임스탬프라고 가정
- 실시간 스트리밍 처리·윈도우 자동 슬라이딩 — 지금은 노트북에서 구간을 손으로
  슬라이싱(`words[0:29]`)해 한 번 계산해본 것뿐
- 전송 계층 — 서버 코드 없이 노트북 셀을 직접 실행하는 형태뿐입니다

## 2. 출력 계약

`SpeedResult` (Pydantic) 모델이 다운스트림과의 접점입니다.

```json
{
  "speed": 428.57,
  "level": "fast"
}
```

| 필드 | 의미 |
|---|---|
| `speed` | 판정 구간의 CPM(분당 발화 글자 수). `float` |
| `level` | `"slow" \| "normal" \| "fast"`. `speed < 275`면 `slow`, `speed > 350`면 `fast`, 그 사이는 `normal` |

이 모양이 바뀌면 **v2**입니다.

> ⚠️ 지금 노트북 코드는 판정 결과를 `print()`로만 출력하고, `SpeedResult` 인스턴스를 실제로
> 만들어 반환하지는 않습니다. 위 계약은 정의된 스키마 기준이며, 노트북 동작과 완전히
> 일치하지는 않습니다 — [local/README.md](local/README.md)의 "반드시 알아야 할 함정"을
> 참고하세요.

> ### 검증된 것과 검증되지 않은 것을 구분하세요
>
> **계산 공식은 정의돼 있고, 예시 하나로 값이 나오는 것은 확인했습니다.** 글자 수를 실제
> 발화 시간(침묵 제외)으로 나눠 CPM을 구하고, 두 임계값으로 3단계 판정하는 로직이 동작합니다.
>
> **임계값과 일반화는 검증되지 않았습니다.** 275/350이라는 경계값, 15초라는 윈도우 길이,
> "침묵 제외 발화 시간을 분모로 쓴다"는 설계 모두 실제 발표 데이터나 평가셋 없이 손으로 만든
> 예시 하나에 대해서만 확인됐습니다.

### v1을 "완료"라고 부르려면

1. 정답 라벨(구간별 정답 속도 등급)이 있는 실제 발표 STT 데이터셋 구축
2. 임계값(275/350)·윈도우 길이(15초)가 실제 데이터에서 타당한지 검증하고 필요시 재조정
3. 손으로 하는 구간 슬라이싱을 슬라이딩 윈도우 함수로 일반화 (구간 겹침·경계 처리 포함)
4. `SpeedResult`를 실제로 생성해 반환하도록 코드 정리

절차와 명령은 [local/README.md](local/README.md)에 있습니다.

## 5. 파이프라인 상세

### 5-1. 데이터 구조

```
Word        { word: str, start: float(ms), end: float(ms) }
SpeedResult { speed: float, level: "slow" | "normal" | "fast" }
```

### 5-2. 구간 슬라이싱

전체 단어 리스트에서 판정하고 싶은 구간만 잘라 씁니다 (예: `words[0:29]`). 노트북 주석에
`[0:29] [5:31] [12:33]`처럼 겹치는 구간 인덱스가 적혀 있는데, 이는 슬라이딩 윈도우로 확장할
때의 후보일 뿐이고 실제로 계산되는 것은 첫 구간(`words_15s = words[0:29]`) 하나뿐입니다.

### 5-3. CPM 계산

```
total_characters = 구간 내 단어들의 글자 수 합
speak_duration    = 구간 내 각 단어의 (end - start) 합(ms) / 1000   ← 침묵 제외, 실제 "말한" 시간만
cpm = total_characters / speak_duration * 60
```

`total_duration`(구간의 끝-처음, 침묵 포함)이 아니라 **`speak_duration`(침묵 제외)을 분모로
쓰는 것이 의도된 설계**입니다 — 말 사이 침묵이 길수록 같은 글자 수라도 체감 속도는 빨라지므로,
침묵을 CPM에 포함하면 실제보다 느리게 판정됩니다.

### 5-4. 임계값 판정

```
cpm < SLOW_THRESHOLD(275)  → "slow"
cpm > FAST_THRESHOLD(350)  → "fast"
그 외                       → "normal"
```

## 6. 알려진 한계

- **예시 1건뿐** — 손으로 만든 단어 시퀀스 하나(약 21초, 뒤로 갈수록 빨라지는 패턴)로만
  확인했고, 실제 STT 출력이나 다양한 발화 패턴에 대한 검증은 없습니다.
- **임계값 근거 없음** — 275/350이라는 CPM 경계값이 어디서 왔는지, 실제 발표에서 타당한지
  확인되지 않았습니다.
- **슬라이딩 윈도우 미구현** — 여러 구간을 겹쳐가며 실시간으로 갱신하는 로직은 주석의 인덱스
  후보로만 존재하고, 실제로 함수화되어 있지 않습니다.
- **`SpeedResult` 미사용** — 스키마는 정의돼 있지만 노트북은 결과를 `print()`만 하고 실제
  `SpeedResult` 인스턴스를 만들지 않습니다.
