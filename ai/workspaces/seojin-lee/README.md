# seojin-lee

**Pitch Coach**의 자연어처리(NLP) 파트를 담당합니다.

발표 대본과 평가 기준처럼 **자유 형식 텍스트**를 LLM으로 구조화해
다른 파트가 그대로 소비할 수 있는 형태로 바꾸는 것이 이 워크스페이스의 범위입니다.

---

## 프로젝트

| 프로젝트 | 무엇을 하는가 | 상태 |
|---|---|---|
| [script-parser](script-parser/) | 발표 대본 전체 텍스트를 간단한 전처리 및 **슬라이드 단위**로 분리하고, 슬라이드별 **키워드**를 추출 | v1 개발 중 (local) |
| [evaluation-criteria](evaluation-criteria/) | 사용자가 자연어로 작성한 발표 평가 기준을 **판단 가능 / 정보 부족 / 판단 불가**로 분류 | v1 개발 중 (local) |

## 이 워크스페이스의 규칙

### 버전 축이 두 개입니다

헷갈리기 쉬우니 먼저 짚습니다.

| | 무엇 | 어디서 올라가는가 |
|---|---|---|
| **모델 버전** (`v1`, `v2`, …) | 모델의 **출력 의미**가 바뀔 때 | `workspaces/seojin-lee/<project>/vN/` |
| **릴리스 버전** (`v1.0.0`, …) | 제품으로 묶어 내보낼 때 | `releases/vX.Y.Z/<project>/` |

둘은 독립입니다. 모델 `v1`이 릴리스 `v1.0.0`과 `v1.1.0`에 모두 실릴 수 있고,
반대로 모델 `v2`를 만드는 동안 릴리스는 계속 `v1`을 내보낼 수도 있습니다.

**모델 버전을 올리는 기준**: 출력 스키마 변경, 분류 기준 변경, 사용 모델 교체처럼
**소비자가 받는 결과의 의미가 달라지는** 변화. 프롬프트 문구 다듬기나 파라미터 튜닝은
버전을 올리지 않습니다 — 그건 각 프로젝트가 기록하는 config hash가 추적합니다.

### `local` / `deploy`

같은 모델을 **어디서 돌리느냐**입니다. 모델 자체는 하나이므로, 두 환경은
`vN/README.md`(모델 기술 레퍼런스)를 공유하고 환경별 README만 따로 둡니다.

- `local/` — 실험·평가 리그. 프롬프트를 짜고, 테스트 대본으로 결과를 확인하고, 지표를 재는 곳
- `deploy/` — 서비스 투입용 패키징

### 문서 규칙

각 레벨의 `README.md`가 맡는 범위:

| 레벨 | 답해야 하는 질문 |
|---|---|
| `<project>/README.md` | 이 프로젝트가 무엇이고, 어느 버전이 있고, 어디서 시작하나 |
| `<project>/vN/README.md` | 이 모델이 무엇을 보장하고 무엇을 보장하지 않는가 (**전체 기술 레퍼런스**) |
| `<project>/vN/local/README.md` | 어떻게 돌리고 어떻게 개발하나 (셋업·명령·함정) |

## 환경변수

`script-parser`, `evaluation-criteria` 둘 다 읽는 환경변수입니다. 루트 `.env.example`에
반영이 필요하면 여기를 참고하세요.

| 변수 | 효과 |
|---|---|
| `OPENAI_BASE_URL` | 호출할 LLM 엔드포인트 |
| `OPENAI_API_KEY` | 해당 엔드포인트 인증 키 |
| `OPENAI_MODEL` | 사용할 모델 이름 (예: `openai/gpt-5.6-luna`) |
