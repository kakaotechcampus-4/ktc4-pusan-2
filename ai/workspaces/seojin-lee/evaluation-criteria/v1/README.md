# v1 — 평가 기준 3분류 (evaluable / need_more_info / not_evaluable)

사용자가 자유 문장으로 작성한 발표 평가 기준을 받아, 현재 발표 분석 시스템이
**판단할 수 있는지**, **판단할 수 있지만 정보가 부족한지**, **아예 판단하지 않는지**
세 가지로 분류하는 첫 번째 모델입니다.

```
자연어 평가 기준 ──▶ LLM (structured output) ──▶ EvaluationCriteriaAnalysis
                    system prompt로 판단 가능      (evaluable / need_more_info /
                    항목 목록 + 분류 규칙 고정         not_evaluable)
```

이 문서는 **v1 모델의 전체 기술 레퍼런스**입니다 — 분류 기준 정의, 출력 계약,
알려진 한계. `local`과 `deploy`가 공유합니다.

> **코드를 돌려보려면 [local/README.md](local/README.md)** 로 가세요.
> 설치 절차, 노트북 실행 방법 같은 작업용 내용은 거기에 있습니다.

## 1. v1의 범위

**하는 것**

- 입력 문장을 평가 요소 단위로 분해하고, 각 요소를 아래 세 범주 중 하나로 분류
- **판단 가능 요소 목록을 고정**: 발표 시간, 말하기 속도, 발음, 억양, 음량, 멈춤/침묵, 필러,
  시선 처리, 대본 사용 여부, 대본 의존도, 실제 발화와 대본의 의미적 유사도
- 구체적 기준값이 없는 판단 가능 요소는 `need_more_info`로 분리해, 임의로 수치를
  만들어내지 않음
- 동일 요소가 여러 번 등장하면 하나로 통합

**하지 않는 것**

- 판단 불가 요소(발표 주제, 자료 신뢰도, 용모, 질의응답 등)에 **값을 추출**하지 않음 —
  `not_evaluable`에는 요소 이름만 담김
- 전송 계층 — 서버 코드 없이 노트북에서 `structured_output.invoke()`를 직접 호출하는
  형태뿐입니다

## 2. 출력 계약

`EvaluationCriteriaAnalysis` (Pydantic) 모델이 다운스트림과의 접점입니다.

```json
{
  "evaluable": [
    { "key": "발표 시간", "value": "10분 이내" },
    { "key": "대본 사용", "value": true }
  ],
  "need_more_info": [
    { "key": "말하기 속도", "value": "너무 빠르지 않도록 해야 함" }
  ],
  "not_evaluable": ["발표 주제의 창의성", "질의응답"]
}
```

| 필드 | 의미 |
|---|---|
| `evaluable[].key/value` | 판단 가능 요소이며 구체적 기준값까지 주어진 경우. `value`는 `str \| bool \| int \| float \| null` |
| `need_more_info[].key/value` | 판단 가능 요소이지만 구체적 기준이 없는 경우. `value`는 입력에서 확인된 현재까지의 값(기준 미포함)이며 항상 `str` |
| `not_evaluable` | 시스템이 애초에 판단하지 않는 요소 이름 목록. 값은 담기지 않음 |

세 필드는 해당 항목이 없어도 `[]`로 항상 반환되며 생략되지 않습니다.
이 모양이 바뀌면 **v2**입니다.

> **왜 `dict[str, ...]`가 아니라 key/value 리스트인가**: OpenAI 구조화 출력의
> `json_schema` strict 모드는 키가 고정되지 않은 필드(자유 키 dict)를 지원하지 않습니다.
> 그래서 `evaluable`/`need_more_info`를 `{key, value}` 항목의 리스트로 표현해 strict 모드를
> 그대로 유지합니다 (function tools가 아니라 response_format 기반이라 `reasoning_effort`와도
> 충돌하지 않습니다).

| 검증 방식 | ⚠️ **수동 확인뿐** — 노트북에 적어둔 예시 입력·출력 쌍을 사람이 눈으로 검토한 것이 전부이며, 정답 라벨이 있는 평가셋은 없습니다 |
| 정확도 지표 | ⬜ 없음 — 분류 정확도(evaluable/need_more_info/not_evaluable 오분류율)는 미측정 |
| 전송 계층 | ⬜ 없음 — 노트북 인프로세스 호출뿐 |
| CI | 없음 |

> ### 검증된 것과 검증되지 않은 것을 구분하세요
>
> **분류 규칙은 예시 기반으로 설계됐습니다.** system prompt에 판단 가능 요소 목록,
> 세 범주의 정의, 각 범주별 예시가 명시돼 있고, 5개 예시 입력에서 규칙대로 동작하는
> 것을 확인했습니다.
>
> **경계 사례의 일관성은 검증되지 않았습니다.** "적절히"·"엄수" 같은 모호한 수식어를
> `need_more_info`로 보낼지 `evaluable`로 볼지의 경계, 새로운 표현으로 같은 요소를
> 지칭했을 때의 통합 여부는 정량 평가 없이 프롬프트 지시에만 의존합니다.

### v1을 "완료"라고 부르려면

1. 정답 라벨(요소별 정답 범주 + 값)이 있는 평가셋 구축
2. 범주별 분류 정확도, `key` 통합(중복 제거) 정확도 측정
3. 경계 사례(모호한 수식어, 신규 표현)로 프롬프트 스트레스 테스트
4. 결과에 따라 판단 가능 요소 목록·시스템 프롬프트 규칙 보강

절차와 명령은 [local/README.md](local/README.md)에 있습니다.

## 5. 파이프라인 상세

### 5-1. Structured Output 정의

```
EvaluableItem      { key: str, value: str | bool | int | float | None }
NeedMoreInfoItem   { key: str, value: str }
EvaluationCriteriaAnalysis {
  evaluable: EvaluableItem[]
  need_more_info: NeedMoreInfoItem[]
  not_evaluable: str[]
}
```

`model.with_structured_output(EvaluationCriteriaAnalysis)`로 LLM 출력 스키마를 고정합니다.

### 5-2. 시스템 프롬프트 규칙

- 먼저 해당 평가 기준이 **현재 시스템에서 판단 가능한 요소 목록**(§1)에 속하는지 확인
- 판단 가능 + 구체적 기준 있음 → `evaluable`
- 판단 가능 + 구체적 기준 없음 → `need_more_info` (입력에 없는 수치·기준은 임의로 생성하지 않음)
- 판단 불가 → `not_evaluable` (이름만, 값 없음)
- 동일 평가 요소가 여러 번 등장하면 하나로 통합하고, 입력 의미를 유지하며 적절한 `key`로 정리
- 세 필드는 해당 사항이 없어도 빈 리스트로 항상 반환 — 필드 자체를 생략하지 않음

## 6. 알려진 한계

- **평가셋 부재** — 지금까지는 5개 남짓의 예시 입력을 사람이 육안으로 확인한 것이 유일한 검증입니다.
- **경계 사례의 일관성 미검증** — 모호한 수식어("적절히", "엄수")를 `need_more_info`로 보낼지,
  같은 의미를 다르게 표현한 요소를 하나의 `key`로 통합할지는 프롬프트 지시에만 의존하며
  실제 일관성은 확인되지 않았습니다.
- **판단 가능 요소 목록이 하드코딩** — 발표 분석 시스템이 새 지표를 추가하면 이 목록과
  system prompt를 수동으로 갱신해야 합니다.
