# v1 — 대본 문장 단위 전달 평가

발표자가 **슬라이드 대본의 내용을 전달했는가**를 대본 문장 · Key Point · 핵심 수치 단위로 판정하는 첫 번째 모델입니다.
발음 때문에 음성 인식이 다른 말로 적었을 수 있는 곳은 **판단을 보류**하고 위치만 남깁니다.

```
① 대본 분석   대본 JSON ──▶ 정규화 ──▶ 규칙 분석 ──▶ LLM 1차 분석 ──▶ 코드 정리·검증 ──▶ LLM 최종 결론 ──▶ 평가 기준 (DB)
② STT 평가    STT ──▶ 정규화 ──▶ 규칙 분석 ∥ LLM 문장 판정 ──▶ 병합·충돌 검사 ──▶ (LLM 교차 검증) ──▶ Key Point 판정 ──▶ 점수 (DB)
```

이 문서는 **v1 모델의 전체 기술 레퍼런스**입니다 — 출력 계약, 단계별 동작, 설계 근거, 측정 결과, 한계. `local`과 `deploy`가 공유합니다.

> **코드를 돌려보려면 [local/README.md](local/README.md)** 로 가세요.
> 설치 절차, 실행 명령, 데이터 추가 방법, 함정 같은 작업용 내용은 거기에 있습니다.

## 1. v1의 범위

**하는 것**

- 한국어 발표 대본(슬라이드별 JSON)을 **평가 기준**으로 만듭니다: 문장별 역할, 핵심 주장, Key Point(중요도 · 근거 문장), 핵심 사실(수치 · 이름)
- 슬라이드별 STT를 **대본 문장마다** 판정합니다: 전달(`said`) / 일부(`partial`) / 빠짐(`missing`) / 모순(`contradicted`), 근거 STT 문장 번호와 이유 포함
- 핵심 수치를 **값으로** 검증합니다: 아라비아 숫자와 한글로 읽은 수(`사십이 퍼센트`, `천이백사십만 건`, `오후 여섯 시`)를 같은 정규형으로 비교하고, 어림 표현(`40퍼센트 넘게`)과 다른 값을 구분합니다
- 발음이 비슷한 다른 말(`노쇼` → `노조`, `삼십 분` → `사십 분`)은 **판단 보류** — 점수 비율에서 빼고 개수와 위치만 남깁니다
- 점수 3개(내용 전달 · 수치 정확도 · 대본 충실도)와 비슷한 말 개수를 **코드가** 계산합니다
- LLM 응답을 캐시해, 같은 입력·프롬프트·모델이면 다시 부르지 않습니다. 대본을 고치면 바뀐 슬라이드만 다시 분석합니다

**하지 않는 것**

- 음성 인식 — Deepgram 결과를 입력으로 받습니다
- 슬라이드 경계 추정 — 웹이 슬라이드 넘김을 기록해 **슬라이드별 STT** 를 준다고 전제합니다
- 발표자 실수인지 음성 인식 오류인지 **최종 판단** — 비슷한 말은 위치와 함께 넘기고, 판단은 코칭(리뷰) agent 가 합니다
- 전달력(말 속도 · 간투사 빈도 · 시선) 평가 — 여기서는 **내용** 만 봅니다
- 코칭 문구 생성, 서비스 API · 전송 계층

## 2. 출력 계약

다운스트림과의 접점은 DB 테이블 세 개입니다. 전체 필드는 노트북의 pydantic 모델(`EvaluationRubric`, `SlideEvaluation`, `SimilarItem`)이 단일 진실 원천입니다.

### 2-1. 평가 기준 — `evaluation_rubrics.rubric_json` (① 이 쓰고 ② 가 읽음)

| 필드 | 뜻 |
|---|---|
| `meta` | `rubric_id`, 대본 이름, 슬라이드 번호, `content_hash`, 스키마 버전, LLM 모델, 1차·최종 설정 해시 |
| `sentences`, `sentence_roles` | 정규화한 대본 문장과 문장별 역할 `claim` / `evidence` / `detail` / `skip` |
| `core_claim` | 슬라이드의 핵심 주장 한 문장 |
| `key_points[]` | `id`, `content`, `importance`(`critical` / `high` / `normal`), `sentence_indices`(근거 문장), `source_quote`, `key_terms`, `fact_ids` |
| `critical_facts[]` | `id`, `type`, `value`(대본 표기), `normalized`(비교용 정규형), `numeric_value`, `unit`, `qualifier`, `spans`, `sentence_indices`, `source`(`rule` / `llm`), `key_point_ids`, `importance` |
| `keywords`, `warnings`, `review_changes`, `name_decisions` | TF-IDF 키워드, 최종 경고, 최종 결론이 1차에서 바꾼 점, 이름·용어 후보 판정 |

```json
{"id": "CF10", "type": "percentage", "value": "18%", "normalized": "18%", "numeric_value": 18.0, "unit": "%",
 "qualifier": null, "sentence_indices": [3], "source": "rule", "key_point_ids": ["KP4"], "importance": "high"}
```

### 2-2. 슬라이드 평가 — `slide_evaluations.evaluation_json` (② 가 쓰고 소비자가 읽음)

| 필드 | 뜻 |
|---|---|
| `scores` | `content_coverage`, `critical_fact_accuracy`(사실이 없으면 `null`), `script_fidelity`, `similar_words`, `similar_numbers` (§8) |
| `sentences[]` | 대본 문장별 `status` · `first_status`(LLM 1차) · `evidence`(T번호) · `reason` · `confidence` · `lexical_coverage` · `fact_statuses` · `similar_ids` · `conflicts` · `verified` |
| `key_points[]` | Key Point 별 `status`(`covered` / `partial` / `missing` / `contradicted`) — **근거 문장 판정을 모은 값** (§7-9) |
| `critical_facts[]` | 사실별 `status`(`matched` / `approximate` / `mismatched` / `missing` / `sound_alike` / `unverified`), STT 표기, 원인 |
| `similar_items[]` | 비슷한 말 (§2-3) |
| `stt_sentences` | 정규화한 STT 문장 — `evidence` 의 T번호가 가리키는 원문 |
| `rubric_id`, `alignments`, `fidelity`, `verification` | 채점에 쓴 평가 기준, 문장 정렬, 충실도 세부, 교차 검증 대상 |

판정 값의 뜻:

| 문장 `status` | 뜻 | 사실 `status` | 뜻 |
|---|---|---|---|
| `said` | 뜻이 전달됨 (의역 포함, 핵심 수치·이름까지) | `matched` | 같은 값을 말함 |
| `partial` | 일부만 (수치를 흐리거나 내용 일부만) | `approximate` | 어림해 말함, 사실은 맞음 |
| `missing` | 없음 | `mismatched` | 다른 값을 말함 (발음이 전혀 다르거나 음절 순서가 바뀜) |
| `contradicted` | 다른 수치 · 반대 내용 | `sound_alike` | 발음이 비슷한 다른 말 — **판단 보류** |

### 2-3. 비슷한 말 — `similar_items` (한 행씩)

| 열 | 뜻 |
|---|---|
| `kind`, `script_text`, `stt_text` | `word` / `number`, 대본 표현, STT 표현 |
| `script_sentence_index`, `script_start`, `script_end` | 대본 문장 번호와 정규화 대본 텍스트 안의 위치 |
| `stt_sentence_index`, `stt_start`, `stt_end` | STT 문장 번호(T번호)와 정규화 STT 텍스트 안의 위치 |
| `stt_raw_start`, `stt_raw_end` | **원본 STT** 안의 위치 — 간투사를 지우기 전 텍스트 기준. Deepgram 단어 타임스탬프와 맞춰 녹음 구간을 찾는 데 씁니다 |
| `fact_id`, `key_point_ids` | 관련 Critical Fact, 이 자리가 걸린 Key Point |
| `rule_guess`, `signals` | 규칙 추정(`asr_error` 인식 오류 쪽 / `speaker_error` 발표자 실수 쪽)과 근거 신호 — **참고용** |

이 세 모양의 **의미**가 바뀌면 v2 입니다.

실제로 실행해 확인한 현재 상태입니다.

| 항목 | 상태 |
|---|---|
| 노트북 | ✅ `script_analysis_pipeline.ipynb`, `stt_evaluation_pipeline.ipynb` 모두 에러 없이 끝까지 실행. 캐시가 있으면 각각 약 25초 · 40초 (API 호출 0회) |
| 데이터 | ✅ 가상 대본 2개(슬라이드 9 + 11장), 가상 STT 18개(대본당 9개 시나리오)와 문장별 정답 라벨 |
| LLM | OpenAI 호환 API. 검증한 모델은 `gpt-5.6-luna` (환경 변수 `OPENAI_MODEL`) |
| 정확도 | ⚠️ **가상 데이터로만 측정.** 가상 STT 와 정답 라벨을 같은 작성자가 만들어 실제보다 쉬울 수 있습니다 (§11) |
| 테스트 · CI | ⚠️ 없음. 규칙 부분의 회귀 확인은 대본 분석 노트북 11장의 `assert`(수 파서 사례 포함)뿐입니다 |
| 설계 문서 | 노트북 안의 설명이 전부입니다 — 각 장 앞의 마크다운이 그 장의 설계와 근거를 설명합니다 |

> ### 검증된 것과 검증되지 않은 것을 구분하세요
>
> **규칙 부분은 결정적이고 검증됐습니다.** 수 파서(한글 숫자 포함), 수치 검증, 비슷한 말의 위치는
> 가상 데이터 전체에서 정답과 일치했고, 같은 입력은 늘 같은 결과입니다.
>
> **LLM 판정의 실제 정확도는 검증되지 않았습니다.** 11장 정확도는 가상 데이터에 대한 값이고,
> 실제 발표자의 말투와 실제 Deepgram 출력에서는 낮아질 수 있습니다.

### v1을 "완료"라고 부르려면

1. 실제 발표 연습의 **슬라이드별 Deepgram 결과**와 녹음 5~10개를 모아 STT JSON 형식으로 저장 ([local/README.md](local/README.md))
2. 대본 문장마다 정답 라벨 작성 (§10 형식)
3. STT 노트북 3-2장 **문장 분리 점검** → 11장 **정답 비교** → 12장 **반복 채점** — 여기서 처음으로 실제 정확도가 나옵니다
4. 필요하면 임계값 조정 (`LEXICAL_PRESENT`/`LEXICAL_ABSENT`, `WORD_DISTANCE`, `FILLER`, `LONG_SENTENCE`)
5. `deploy/` 설계 — 서비스 API, DB, 코칭 agent 와의 인터페이스

## 5. 아키텍처

```text
[대본 JSON]                              [발표 연습: 슬라이드별 STT]
     │                                              │
① 대본 분석 (대본 등록·수정 시)                 ② STT 평가 (연습할 때마다)
     │                                              │
     ▼                                              ▼
evaluation_rubrics ───────────────────────▶ slide_evaluations + similar_items ──▶ 코칭(리뷰) agent
```

**역할 분담** — 수치 · 날짜 · 이름 · 정렬 · 점수처럼 규칙으로 확실하게 정할 수 있는 것은 코드가,
어떤 문장이 핵심인지 · 말한 내용이 대본 문장의 뜻을 전달했는지처럼 의미를 이해해야 하는 것은 LLM 이 맡습니다.
LLM 은 **판정만** 하고 점수는 매기지 않습니다.

### LLM 호출

| 언제 | 호출 | 비고 |
|---|---|---|
| 대본 등록 | 슬라이드당 2회 | 1차 분석 + 최종 결론 |
| 대본 수정 | 바뀐 슬라이드만 2회 | 캐시 키가 대본 내용 해시 |
| 발표 연습 1회 | 슬라이드당 1회 + 충돌한 문장이 있는 슬라이드만 1회 | 가상 데이터에서 교차 검증은 슬라이드의 약 23% (180장 중 41장) |

### 캐시

| 캐시 | 키 | 무효화되는 때 |
|---|---|---|
| `semantic_cache` (①1차) | 대본 내용 해시 + 설정 해시 | 대본 · 프롬프트 · 출력 스키마 · 모델이 바뀜 |
| `final_cache` (①최종) | 입력 메시지 해시 + 설정 해시 | 위 + 규칙 분석 결과나 1차 결과가 바뀜 |
| `stt_llm_cache` (②) | `kind`(semantic / verifier, 반복 채점은 `#k`) + 입력 메시지 해시 + 설정 해시 | STT · 평가 기준 · 프롬프트 · 스키마 · 모델이 바뀜 |

## 6. 대본 분석 상세

`script_analysis_pipeline.ipynb`. 괄호는 노트북의 장 번호입니다.

### 6-1. 입력과 정규화 (1·2장)

대본 JSON 은 `[{"slide_number": 1, "script": "…"}, …]` 입니다. 정규화는 NFKC, 따옴표 통일, 공백 정리, **Kiwi 문장 분리**입니다.
대본 내용 해시(`content_hash`)가 캐시와 재분석의 기준입니다.

### 6-2. 규칙 분석 (3장)

**한국어 수 표기 파서 (3-1)** — `1,240만`, `1만 9천`, `2억 3천만` 같은 혼합 표기와 한글로 읽은 수(`사십이`, `만 구천`, `십일 점 사`),
고유어 수사(`세 가지`, `열두 곳`, `스물다섯 명`)를 값으로 바꿉니다. STT 평가도 같은 파서를 씁니다.

**Critical Fact Parser (3-2)**

| type | 예 (표기 → 정규형) |
|---|---|
| `percentage` | `약 42퍼센트` → `42%` + 한정어 `약`, `15~20%` → `15%`, `20%`, `사십이 퍼센트` → `42%` |
| `money` | `약 24억 원` → `2,400,000,000원`, `만 구천 원` → `19,000원` |
| `quantity` | `약 1,240만 건` → `12,400,000건`, `여섯 배` → `6배`, `열두 곳` → `12곳` |
| `duration` / `date` / `time` | `8주 동안` → `8주` / `2026년 상반기` → `2026-H1`, `이천이십오 년 삼 월` → `2025-03` / `오후 여섯 시 반` → `18:30` |
| `ratio` / `number` | `3:1`, `삼 대 일`, `일대일` → `1:1` / `4 곱하기 6` → `4×6` |
| `proper_noun` / `term` | 영문 이름(`SeatFlow`, `XGBoost`), Kiwi 고유명사, LLM 이 보탠 핵심 용어 |

- 정규식은 "수 + 단위" 모양의 **후보**만 찾고, 단위가 진짜 단위인지는 **Kiwi 형태소 경계**로 확인합니다
  (`24억 원` 의 `원` 은 인정, `3원칙` 의 `원` 은 `원칙` 의 일부라 버림). 한글 수는 Kiwi 가 수사(NR)로 분석할 때만 인정합니다
  (`이 분이 오셨다` 의 `이` 는 관형사).
- 패턴은 우선순위 순서로 적용하고, 앞 패턴이 잡은 구간은 뒤 패턴이 다시 잡지 않습니다. 서수(`1단계`)는 제외합니다.

**TF-IDF 키워드 (3-3)** — 문서 집합 = 한 발표의 슬라이드들. 토큰은 Kiwi 명사 + 명사 2-gram.

### 6-3. LLM 1차 분석 (4장) — 슬라이드당 1회

대본 문장에 `[S번호]` 를 붙여 주고, 다음 순서로 답하게 합니다.

1. **문장 역할** — `claim`(핵심 주장, 슬라이드당 정확히 1문장. 팀 소개·목차처럼 나열만 하는 슬라이드에는 없음) / `evidence`(근거) / `detail`(세부) / `skip`(인사·전환)
2. **핵심 주장** 한 문장
3. **Key Point** — 내용, 근거 문장 번호, 핵심 용어

근거를 문장 번호로 받기 때문에 Key Point 가 대본의 어느 부분에서 왔는지 코드가 정확히 압니다.

### 6-4. 1차 정리 · 검증 (5장, 코드)

- **중요도는 문장 역할로 정합니다**: 근거 문장에 `claim` 이 있으면 `critical`, `evidence` 면 `high`, 나머지 `normal`.
  채점 가중치 `SCORE_WEIGHT` = critical 3 / high 2 / normal 1.
- **핵심 용어 거르기**: 영문·고유명사는 통과, 4어절 이상 구절과 발표 전체에 두루 나오는 일반 명사는 제외.
- **사실 ↔ Key Point 연결**: Key Point 가 그 사실을 직접 말하면(핵심 용어로 지목했거나, 내용에 같은 수치·이름이 있고 근거 구간 안에 나옴) 연결합니다.
  어느 Key Point 도 직접 말하지 않는 사실은 근거 구간이 그 사실을 품은 Key Point 가 하나뿐일 때만 연결합니다.
- **검증 경고**: 역할이 빠진 문장, critical 이 없는 슬라이드, 대본에 없는 수치를 말한 Key Point 등.

### 6-5. LLM 최종 결론 (6장) — 슬라이드당 1회

1차 분석 + 규칙 분석 결과 + 검증 경고를 함께 주고 최종 판단(문장 역할, 핵심 주장, Key Point, 이름·용어 후보 판정, 바꾼 점)을 받습니다.
코드가 이를 평가 기준으로 조립해 저장합니다 (7~9장).

### 6-6. 대본 수정 시 재분석 (10장)

대본을 고치면 내용 해시가 바뀐 슬라이드만 다시 분석합니다. 한 슬라이드를 고치면 호출은 최대 2회입니다.

## 7. STT 평가 상세

`stt_evaluation_pipeline.ipynb`. 대본 분석 노트북을 `%run` 으로 불러와 함수와 평가 기준을 그대로 씁니다.
입력 STT 는 `{"script_name", "take_id", "scenario", "slides": [{"slide_number", "stt"}]}` 입니다.

### 7-1. STT 정규화 (2장, 규칙)

대본과 같은 정규화에 **간투사 제거**(단독으로 쓰인 `음 · 어 · 으 · 엄 · 흠 · 아 · 에`)와 **바로 반복된 말 제거**(`그 그 결과` → `그 결과`)를 더합니다.
한글로 적힌 숫자는 **바꾸지 않고** 수 파서로 읽습니다. STT 문장에는 `[T0]`, `[T1]` … 번호를 붙입니다.
LLM 으로 정규화하지 않는 이유는 §12 에 있습니다.

### 7-2. 문장 정렬과 대본 충실도 (3장, 규칙)

- **내용 형태소** — 조사·어미·간투사를 버리고 명사, 동사·형용사 어간, 수사, 영문, 부사만 남깁니다. 명사에 붙은 접미사는 한 단어로(`이용`+`률` → `이용률`),
  수치는 정규형 토큰(`<percentage:42%>`)으로 바꿉니다.
- **문장 정렬** — 대본 문장마다 STT 연속 1~3문장 구간 중 대본 형태소가 가장 많이 나온 구간을 찾습니다(비율이 같으면 짧은 구간). 이 비율이 충돌 검사의 근거입니다.
- **대본 충실도** — 순서를 지킨 형태소 일치(`SequenceMatcher`)의 recall · precision 조화평균. '대본대로 말했는가'를 봅니다.
- **문장 분리 점검 (3-2)** — 연습마다 STT 문장 길이, 긴 문장 수, 정렬 구간 크기, 남은 간투사 후보를 보여 줍니다. 실제 데이터를 넣었을 때 먼저 봅니다.

### 7-3. 핵심 사실 검증 (4장, 규칙)

| 결과 | 조건 |
|---|---|
| `matched` | 같은 값. 수치는 STT 에서도 같은 수 파서로 읽어 정규형끼리 비교 |
| `mismatched` | 같은 값은 없고, 정렬된 STT 구간(없으면 앞뒤 한 문장)에 같은 종류·단위의 다른 값. STT 의 한 값은 한 사실에만 씀 |
| `missing` | 어디에도 없음 |
| `unverified` | 규칙으로 못 찾은 **영문 이름** — STT 가 한글로 적었을 수 있어 5장 LLM 이 확인 |

### 7-4. 다른 수치의 원인 신호 (4-2장, 규칙)

두 수를 **소리 내어 읽은 형태**(`312` → `삼백십이`, 시각 `18:00` → `여섯시`)로 비교합니다.

| 발음 관계 | 예 | 처리 |
|---|---|---|
| 어림 표현 + 방향·차이(30% 이내)가 맞음 | 42% → `40퍼센트 넘게` | `approximate` (절반 인정) |
| 음절 순서만 바뀜 | 76% → `육십칠 퍼센트` | `mismatched` — 음성 인식은 음절 순서를 바꾸지 않음 |
| 발음이 전혀 다름 | 600만 원 → `팔백만 원` | `mismatched` |
| 발음이 비슷한 음절 하나 차이 · 음절 하나 빠짐/더해짐 · 조금 비슷함 | 312명 → `사백십이 명`, 42% → `40%`, `여섯 시` → `다섯 시` | **비슷한 말 → 판단 보류** (7-5) |

대본에 원래 있던 한정어(`약 18%` 의 `약`)는 발표자의 어림으로 보지 않습니다.

### 7-5. 비슷한 말 찾기 (4-3장, 규칙) — 판단 보류

1. 7-4 에서 '비슷한 수치' 로 본 것
2. 대본 문장과 정렬된 STT 를 형태소 단위로 맞춰 **같은 자리에서 바뀐 표현**
   - 수치 → 비슷한 수치 (같은 수치를 다른 문장에서 맞게 말해 7-3 에서 빠진 경우도 잡힘)
   - 단어 → 단어: 대본 명사가 그 자리에서 빠지고 **발음 거리** 0.34 이하인 새 말이 나옴

발음 거리 = 음절 단위 편집 거리 / 긴 쪽 음절 수. 음절을 바꾸는 비용은 초성·중성·종성 중 다른 수 / 3, 셋 다 다르면 1.5.
`모델`↔`모텔` 0.17, `노쇼`↔`노조` 0.33 은 비슷한 말, `월요일`↔`금요일` 0.5 는 아닙니다.
비슷한 말에 걸린 수치·이름은 `sound_alike` 가 되어 점수 비율에서 빠지고, 위치와 함께 `similar_items` 에 저장됩니다.

### 7-6. LLM 의미 평가 (5장) — 슬라이드당 1회

판정 대상 대본 문장(`[S번호]`, 문장 속 핵심 수치·이름)과 번호를 붙인 STT(`[T번호]`)를 주고, **대본 문장마다**
근거 STT 문장 → 이유 → 판정(`said` / `partial` / `missing` / `contradicted`) → 확신도 순서로 받습니다.
규칙이 못 찾은 영문 이름도 같은 호출에서 확인합니다. **규칙 결과는 입력에 넣지 않습니다** — 독립적으로 판정해야 6장에서 서로의 실수를 찾을 수 있습니다.

### 7-7. 문장별 병합 · 충돌 검사 (6장, 코드)

| 충돌 | 조건 (문장 하나 기준) |
|---|---|
| `contradicted` | 모순 판정은 항상 다시 확인 |
| `low_confidence` | 확신도 low |
| `evidence_invalid` | missing 이 아닌데 유효한 근거 문장이 없음 |
| `fact_missing` | said 인데 이 문장의 수치·이름이 STT 에 없음 |
| `sound_alike` | 비슷한 말이 있는데 said 가 아님 |
| `speaker_changed` | 발음이 전혀 다른 수치를 말했는데 contradicted 가 아님 |
| `approximation` | 어림해 말했는데 said |
| `fact_present` | missing 인데 이 문장에만 있는 수치를 STT 에서 찾음 |
| `lexical_present` / `lexical_absent` | missing 인데 단어 비율 ≥ 0.6 / said 인데 < 0.2 |

### 7-8. LLM 교차 검증 (7장) — 충돌한 문장이 있는 슬라이드만 1회

충돌한 문장만 모아, 속한 Key Point · 1차 판정 · 관련 STT 문장 · 수치 확인 · 비슷한 말 · 단어 비율 · 충돌 이유를 보여 주고 다시 판정받습니다.
비슷한 말의 차이는 판정에서 빼라고(대본대로 말한 것으로 보라고) 알려 줍니다.

### 7-9. Key Point 판정 (6장, 코드)

| 근거 문장 판정 | Key Point |
|---|---|
| 하나라도 `contradicted` | `contradicted` |
| 모두 `said` | `covered` |
| 모두 `missing` | `missing` |
| 그 밖 | `partial` |

## 8. 점수

LLM 은 점수를 매기지 않습니다. 모두 코드가 계산하고, 발표 전체 점수는 슬라이드 점수의 가중 평균입니다(개수는 합).

| 점수 | 계산 |
|---|---|
| `content_coverage` | Σ(Key Point 판정 점수 × 중요도 가중치) / Σ(가중치). covered 1 / partial 0.5 / missing 0 / contradicted −0.5, 가중치 3 / 2 / 1. 음수면 0 |
| `critical_fact_accuracy` | Σ(사실 점수 × 가중치) / Σ(가중치). matched 1, approximate 0.5, 나머지 0. **`sound_alike` 는 분자·분모에서 뺌** |
| `script_fidelity` | 7-2 대본 충실도. **비슷한 말 자리의 형태소는 양쪽에서 뺌** |
| `similar_words` / `similar_numbers` | 비율에서 뺀 비슷한 단어·수치의 개수 |

틀린 말(contradicted)은 빠뜨린 것(missing)보다 낮게 봅니다 — 청중에게 잘못된 정보를 준 것이기 때문입니다.

## 10. 가상 데이터와 정답 라벨

실제 발표 대본과 녹음은 저장소에 넣지 않습니다(공개 저장소). 모든 데이터는 가상입니다.

- **대본** — `가상대본1`(도서관 좌석 예측 서비스, 9장), `가상대본2`(동네 빵집 재고 예보, 11장)
- **STT** — 대본마다 9개 시나리오. 문장부호가 거의 없고, 간투사·말 반복·띄어쓰기 오류, 한글로 읽은 숫자, 발음대로 적은 영문 이름이 섞여 있습니다.

| take | 시나리오 | 내용 |
|---|---|---|
| 1 | 충실 | 대본을 거의 그대로 |
| 2 | 의역 | 자기 말로 바꾸고 합치고 순서를 바꿈. 수치·이름은 맞게 |
| 3 | 누락 | 문장 25~40% 빠뜨림, 일부 수치를 `많이` 로 흐림 |
| 4 | 실수 | 틀린 수치, 반대되는 말, 즉흥 발언, 바로 고쳐 말하기 |
| 5 | 혼합 | 의역 · 누락 · 틀린 수치 · 반대되는 말이 한 연습에 |
| 6 | 인식오류 | 맞게 말했지만 음성 인식이 수치를 잘못 적음 + 실제 발표자 실수 |
| 7 | 더듬기 | 간투사 · 말 끊김 · 고쳐 말하기. 수치를 숫자로 적는 STT |
| 8 | 요약 | 슬라이드마다 1~3문장 요약, 수치를 어림해 말함 |
| 9 | 발음 | 음성 인식이 발음이 비슷한 단어·수치를 잘못 적음 + 발표자가 바꿔 쓴 단어 |

**정답 라벨** (`data/stt_labels/<take_id>.json`) — 대본 **문장마다** 발표자가 **실제로 말한 것** 기준으로 적습니다.

| 필드 | 뜻 |
|---|---|
| `status` | `verbatim` / `paraphrased` / `partial` / `missing` / `contradicted` |
| `dropped_values` | 빠뜨린 수치·이름 (→ `partial`) |
| `changed_values` | 발표자가 실제로 틀리게 말한 값 `{"script", "stt"}` (→ `contradicted`) |
| `asr_errors` | 맞게 말했지만 음성 인식이 다르게 적은 값·단어 `{"script", "stt"}` (문장은 `verbatim` 등) |
| `approximated_values` | 어림해 말했고 사실인 값 (→ `partial`) |
| `note`, `additions` | 설명, 대본에 없는 즉흥 발언 |

## 12. 설계 결정

| 결정 | 이유 |
|---|---|
| **LLM 은 대본 문장 단위로 판정, Key Point 는 코드가 모음** | Key Point 를 통째로 판정하면 '몇 문장을 말해야 일부 전달인가' 가 매번 흔들렸습니다. 문장 단위로 바꾸자 요약형 발표 정확도 0.887 → 0.963, 채점마다 판정이 바뀐 Key Point 11 → 7개 |
| **규칙과 LLM 을 독립적으로 돌리고 어긋난 곳만 다시 판정** | LLM 에 규칙 결과를 주면 끌려갑니다. 독립 판정을 비교하면 어느 한쪽의 실수를 찾을 수 있고, 다시 판정하는 비용은 충돌한 곳에만 듭니다 |
| **근거 → 이유 → 판정 순서, 근거 번호는 코드가 확인** | 판정을 먼저 정하고 근거를 끼워 맞추지 않게 합니다 |
| **점수는 코드가 계산** | LLM 이 점수를 매기면 같은 판정도 스케일이 흔들립니다 |
| **수치는 문자열이 아니라 값으로 비교** | STT 는 숫자를 들리는 대로 적습니다(`사십이 퍼센트`). 한글 숫자 파서를 넣자 STT 수치 검증 정확도 74.6% → 100% |
| **발음이 비슷한 말은 판단 보류** | 텍스트만으로는 발표자 실수와 인식 오류를 가릴 수 없습니다. LLM 에게 원인을 판정시켜 봤지만 규칙 추정보다 낫지 않았고(정확도 동일), 수치는 문장에서 늘 자연스러워 오히려 억울한 감점이 생겼습니다. 그래서 비율에서 빼고 위치를 넘깁니다 |
| **STT 정규화는 규칙 (LLM 으로 다시 쓰지 않음)** | LLM 이 문맥에 맞게 고쳐 쓰면(`노조` → `노쇼`) 인식 오류도 발표자 실수도 사라지고, 원본 위치 대응이 깨지고, 결과가 흔들립니다. STT 특유의 표기는 5장 LLM 이 원문을 보며 해석합니다 |
| **대본 분석은 1차 분석 + 최종 결론 2회** | 최종 결론이 검증 경고를 8 → 1 로 줄였습니다. 다만 분석 결과의 흔들림(일관성)은 줄이지 못했습니다 |
| **평가 기준은 대본 등록 때 한 번 만들어 저장** | 같은 대본의 연습끼리 같은 기준으로 비교됩니다. 발표할 때마다 대본을 다시 분석하지 않습니다 |

## 13. 알려진 한계

- **실제 데이터로 측정하지 않았습니다.** 실제 Deepgram 출력의 문장 분리, 인식 오류 양상, 실제 발표자의 말투는 가상 데이터와 다를 수 있습니다.
- **partial / missing 경계**가 가장 흔들립니다 — 채점마다 판정이 바뀐 Key Point 7개 중 5개가 이 경계입니다.
- **한 슬라이드가 채점마다 covered ↔ contradicted 를 오갈 수 있습니다.** 슬라이드 점수 최대 흔들림 60점(발표 전체로는 최대 3.8점).
  리뷰 agent 는 슬라이드 점수 숫자보다 문장 판정과 근거 문장을 보고 말해야 합니다.
- **발음이 비슷한 발표자 실수**(`18%` → `28%`)는 보류되어 점수에 반영되지 않습니다 — 코칭 agent 가 녹음으로 가려야 합니다.
- **대본 분석의 흔들림** — 같은 대본을 다시 분석하면 Key Point 묶음과 이름·용어 사실이 조금 달라집니다(이름·용어 일치율 0.77).
  평가 기준은 한 번 만들어 저장하므로 같은 대본의 연습끼리는 일관되지만, 기준을 다시 만들면 점수가 달라질 수 있습니다.
- **영문 이름의 인식 오류**는 비슷한 말로 잡지 않습니다(한글 표기는 5장 LLM 이름 확인이 봄). `Prophet` → `profit` 같은 경우는 LLM 판단에 맡깁니다.
- **간투사 목록이 짧습니다** — `그`, `저` 같은 말은 뜻이 있을 수 있어 지우지 않습니다. 더듬기 연습에서 `그` 가 14~17번 남습니다 (3-2장 점검).
- **대본 형식** — 무대 지시문(괄호 안 동작 설명 등)이 없는 대본을 전제합니다.

| 증상 | 원인 · 해결 |
|---|---|
| `AssertionError: .env 에 OPENAI_API_KEY / OPENAI_MODEL 이 없다` | `.env` 를 현재 디렉터리부터 위로 찾습니다. `v1/local/` 에서 실행했는지, 상위(예: `ai/.env`)에 키가 있는지 확인 |

| 콘솔에 한글이 깨짐 (Windows) | 노트북을 명령줄에서 실행할 때 `PYTHONIOENCODING=utf-8` |

| 반복 채점이 오래 걸리고 호출이 많음 | STT 노트북 12장은 검증용입니다. `STT_CONSISTENCY_SAMPLES=1` 로 끄세요 |
